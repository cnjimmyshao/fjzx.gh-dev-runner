# 范围与工作链路

## 定位与部署

一个独立的本地接单工具，不属于任何被接入业务项目的业务代码。每台执行电脑安装同一程序，配置自己的机器标识、允许的仓库与发起人、项目目录及 Harness CLI 运行与持久化配置。只处理显式接入的仓库，不自动扫描并启动所有未完成 Issue。

首版接 DeepSeek Harness，不预建多模型适配。不同电脑可承担不同项目，但不承诺任意操作系统和工具链已经兼容；支持矩阵由实际验证逐步形成。

## 职责

接单工具通过本机 `gh` 增量读取 GitHub 评论、检查授权和路由、定位任务会话、启动或续接 Harness CLI 并报告调用异常。它不分析业务需求、不裁决 Finding、不代替维护者作决定，也不建设第二套提交、测试和 Review 编排系统。

模型调用、Agent 循环与工具执行由 Harness 负责。Dev 在目标项目会话中读取该项目的 Issue、AGENTS、Current 和最新决定，按任务要求研究、编码、测试、提交 PR 或提问。目标项目需要的开发环境仍由该执行电脑提供。

## 任务入口

本地约一分钟检查一次已接入仓库的新增评论，不用 Actions 定时扫描，也不为每次空检查调用模型。读取增量而非每分钟重读全部 Issue；初次接入从启用时点开始，不把历史命令全部重放。

授权人显式发布启动／继续命令，并明确唯一执行机，才触发任务。已确认的入口语义（[Issue #9](https://github.com/cnjimmyshao/fjzx.gh-dev-runner/issues/9)）：

- 在已接入仓库的 Open Issue 上设置恰好一个执行机标签 `runner:<machineId>`，标识来自本机配置，不写死在代码里。带多个 `runner:` 标签意味着多台电脑都可能接单，一律不启动。
- 授权人新发布一条独立评论，正文去除首尾空白后恰好为 `@dev`（命令词可配置），才表示开始或继续。首版不把编辑过的评论当命令，不解析引用、代码块或长评论中的命令片段；继续任务须另发新评论。
- 仓库、发起人（`allowedActors`）与唯一目标执行机都符合配置才执行。无标签、多标签、非本机或未授权请求都不启动 Harness；修改标签本身不启动任务，也不自动把已绑定任务迁到另一台电脑。
- 同一任务运行中收到新命令，回复「执行中，本条未启动；结束后重新发指令」，不叠加第二个写入者；首版不自动排队或跨机调度。

链路：

```text
Issue 的授权评论 + 明确执行机
→ 对应电脑通过 gh 接单
→ 按仓库身份 + Issue 编号定位工作目录和绑定
→ 首次启动 Harness headless CLI，记录会话标识
→ 后续启动新进程，在相同目录和匹配配置下续接原会话
→ Dev 按目标项目规则工作，终端／本机日志观察过程
→ 问题／决定回该 Issue，代码变更交付关联 PR
```

同一份新评论不重复执行，同一任务不同时启动两个写入者。多台电脑的机器标识由部署者保持唯一，不建设分布式选主；同一状态目录只允许一个接单进程。

## 会话与工作目录

默认一条任务（仓库身份 + Issue 编号）绑定一个 Harness 开发会话，同时关联执行机、工作目录、分支及已有 PR。不能只按 Issue 数字寻址，也不为每条 Finding 新建会话。

不同任务使用独立目录或 worktree，保护未提交工作；已有 PR 的任务继续原分支，不另开重复 PR。绑定、目录或会话不明确时报告，不凭会话标题猜测，不悄悄从头开发。

任务目录按接入配置二选一：给了部署者的仓库检出就用 `git worktree` 拉独立工作树，或直接用已备好的任务根目录；首次 clone 仍由部署者完成，本工具不代做。绑定存在时只核对目录仍在，不重新准备，避免覆盖任务未提交的工作。

接单工具直接启动本机 Harness headless CLI，不连接或启动 `dsh web`。每次调用是一个执行进程；进程退出不删除任务绑定，后续以已保存的会话标识、相同工作目录和匹配的持久化／profile 配置继续。首次取得标识、续接条件与失败信号已通过一次性本机 CLI 验证确认（见 [CLI 验证报告](../research/2026-09-23-local-harness-cli-first-run-and-resume.md)）；当已装版本自身没有会话身份选项时，用该版本支持的 profile 组合挂本地 runner 补齐，命令仍保持「启动器 + headless profile」。不得将发现历史文件或仅收到启动回执当作正确续接的证据。

重启后应保留必要的评论处理进度和任务绑定，正常重试不重复启动。不承诺跨进程崩溃的端到端 exactly-once；执行是否已经发生不确定时明确报告并核对，不盲目重跑或新建会话。

会话丢失、上下文压缩失败或环境不兼容时保留已有工作并报告。首版不实现自动换会话、迁移会话或无限修复；需要换会话／换机时由维护者确认后记录新绑定。不自动接管已有 Web 会话。

## 凭据与本机调用

GitHub 通信复用实际运行账户已授权的 `gh`；安装 CLI 不等于该账户已登录或具备目标仓库权限。不通过浏览器操作 GitHub，不另建 GitHub 登录系统。

部署者在本机配置并保存 DeepSeek 模型 API Key，通过 Harness 支持的凭据配置或子进程环境提供给它。具体存储与加载方式由实际版本验证后落实。Key 不进入仓库、Issue、任务正文、可见命令行实参或日志；本机凭据文件使用适当受限的访问权限，密钥失效时明确提示，不自行轮换或绕过认证。

首版不实现 Web 启动 URL/cookie 引导、Web API 调用、令牌抓取或 Harness 认证改造。取消的是本机 Web 接入依赖，Harness 调用模型服务仍需要网络与有效模型凭据。

## 权限与可见状态

本机配置和凭证不入库，授权至少绑定仓库、发起人和目标执行机。GitHub 评论是外部输入，不得拼成 shell 命令；启动受信任的 CLI 并将任务作为数据传递。其他权限和沙箱使用已有工具能力，不为内部约定重复制造防御框架。

过程通过终端／本机日志观察，使用当前版本实际提供的输出与退出状态，不承诺逐 token 展示，不新建 Web 界面。明确区分已接单、实际执行中、调用／执行错误、等待维护者和 Dev 报告完成；进程成功退出或出现最终回答，不单独代表测试、Review 或业务验收通过。工具报告自己可核验的进程状态，业务完成与待决事项由 Dev 按目标项目规则报告，不新增模型裁判。

调用方的每次调用都要留下可回查的本机日志（结构化结果与原始 stdout／stderr），并让「命令未启动」「调用失败」「回合非正常结束」三类结果都能在本机与 Issue 上看到原因，不停留在「已接单」。

回写评论保持必要且不刷屏：接单（新建／续接）、执行中未启动、未授权或路由不符、编辑过的评论未启动、调用失败、回合没有正常完成、上次调用结果不确定。公开评论只带执行机、会话标识与任务目录名，本机绝对路径与完整模型输出留在本机。写回失败只记录在本机，不因为反馈失败重跑同一次开发任务。绑定、目录已保存时，进程重启后按原目录续接；发现「已认领未结束」的命令如实报结果不确定，不自动重跑。上次停在准备工作目录阶段（Harness 从未启动）时，恢复后可让该命令在下一轮被重新受理一次，避免已授权的命令被永久跳过。

问题归档到任务所属 Issue，不能把私有任务内容转贴到本公开工具仓库。保留必要本机日志，不默认把完整模型输出公开。

## 首版不做

不搬运旧 Workflow；不建设自动 Review 裁判、自动 merge／部署、中央数据库、跨机抢单、负载均衡、自动接管现有会话、新 Web 管理界面或复杂故障恢复。已有 Codex Review 和人工决策方式保留；如何自动衔接 Review 信号不属于本次基础接单范围。
