# 范围与工作链路

## 定位与部署

一个独立的本地接单工具，不属于任何被接入业务项目的业务代码。每台执行电脑安装同一程序，配置自己的机器标识、允许的仓库与发起人、项目目录和 Harness 实例。只处理显式接入的仓库，不自动扫描并启动所有未完成 Issue。

首版接 DeepSeek Harness，不预建多模型适配。不同电脑可承担不同项目，但不承诺任意操作系统和工具链已经兼容；支持矩阵由实际验证逐步形成。

## 职责

接单工具增量读取 GitHub 评论、检查授权和路由、定位任务会话、投递消息并报告投递或接入异常。它不分析业务需求、不裁决 Finding、不代替维护者作决定，也不建设第二套提交、测试和 Review 编排系统。

Dev 在目标项目会话中读取该项目的 Issue、AGENTS、Current 和最新决定，按任务要求研究、编码、测试、提交 PR 或提问。目标项目需要的开发环境仍由该执行电脑提供。

## 任务入口

本地约一分钟检查一次已接入仓库的新增评论，不用 Actions 定时扫描，也不为每次空检查调用模型。读取增量而非每分钟重读全部 Issue；初次启动不把历史命令全部重放。

授权人显式发布启动／继续命令，并明确唯一执行机，才触发任务。普通讨论、机器人回复、引用或代码块中的命令文字不是自动授权。精确解析和评论编辑语义在实施任务中定稿。

示意链路（尚未实现）：

```text
Issue 的授权评论 + 明确执行机
→ 对应电脑接单
→ 按仓库身份 + Issue 编号定位绑定
→ 首次创建会话；已有任务续接原会话
→ Dev 按目标项目规则工作，原 Harness Web 界面观察
→ 问题／决定回该 Issue，代码变更交付关联 PR
```

同一份新评论不重复投递，同一任务不同时启动两个写入者。任务正在执行时不能再开一个会话抢写同一分支；具体采用排队或明确忙碌响应由实现任务说明。多台电脑的机器标识由部署者保持唯一，不建设分布式选主。

## 会话与工作目录

默认一条任务（仓库身份 + Issue 编号）绑定一个 Harness 开发会话，同时关联执行机、工作目录、分支及已有 PR。不能只按 Issue 数字寻址，也不为每条 Finding 新建会话。

不同任务使用独立目录或 worktree，保护未提交工作；已有 PR 的任务继续原分支，不另开重复 PR。绑定、目录或会话不明确时报告，不凭会话标题猜测，不悄悄从头开发。

会话由已配置的常驻 Harness 实例执行，原 Web 界面应能观察同一会话的消息和状态。后台另起 headless 进程、在磁盘发现历史或收到 API 接受回执，都不单独证明实时观看和续接已经成立。

重启后应保留必要的评论处理进度和任务绑定，正常重试不重复启动。不承诺跨进程崩溃的端到端 exactly-once；投递结果不确定时明确报告并核对，不能盲目再次创建会话。

会话丢失、上下文压缩失败或环境不兼容时保留已有工作并报告。首版不实现自动换会话、迁移会话或无限修复；需要换会话／换机时由维护者确认后记录新绑定。

## 权限与可见状态

本机配置和凭证不入库，授权至少绑定仓库、发起人和目标执行机。GitHub 评论是外部输入，命令正文不得拼入 shell 执行；Harness 控制接口不裸露公网。其他权限和沙箱使用已有工具能力，不为内部约定重复制造防御框架。

明确区分已接收／已投递、实际执行中、等待维护者、执行错误和 Dev 报告完成。投递成功或进程退出不能代表测试、Review、业务验收通过。问题归档到任务所属 Issue，不能把私有任务内容转贴到本公开工具仓库。

## 首版不做

不搬运旧 Workflow；不建设自动 Review 裁判、自动 merge／部署、中央数据库、跨机抢单、负载均衡、自动接管现有会话、新 Web 管理界面或复杂故障恢复。已有 Codex Review 和人工决策方式保留；如何自动衔接 Review 信号不属于本次基础接单范围。
